XML is a text format for structured data. It is the format behind website sitemaps, RSS feeds, many configuration files, vector graphics and the inside of Word, Excel and PowerPoint files. When it is generated by a program it is usually squeezed onto one long line, and when it is typed by a person a single missing tag can break everything.

A formatter fixes both problems. It indents the data so you can read it, and it checks that the structure is sound. This guide explains what well-formed XML is, how to format and minify it, how to find the exact place of an error and what a formatter cannot check.

:::takeaways
- XML is well-formed when every tag is closed, tags are nested correctly and special characters are escaped.
- Formatting adds indentation so you can read the structure, and minifying removes the extra whitespace to save space.
- Error messages give the line and column where the problem was found, which is the quickest way to fix it.
- A formatter checks structure only. It does not validate against a DTD or an XSD schema.
- Escape the ampersand and the angle brackets inside text, or the document breaks.
:::

## What XML looks like

XML marks up data with tags, written in pairs. An opening tag starts an element, a closing tag ends it and the text or other elements between them are its content. Elements can contain other elements, which creates a tree: a document has one root element, which holds children, which hold their own children.

Elements can carry attributes, which are small named values inside the opening tag. An element with no content can be written as a single self-closing tag. The very first line of many files is a declaration that states the version and the character encoding, usually UTF-8.

The structure is strict. Unlike HTML, where browsers forgive many mistakes, an XML program stops at the first error, which is why checking matters.

## What well-formed means

A document is well-formed when it follows the basic rules of the language.

1. There is exactly one root element.
2. Every opening tag has a matching closing tag, or is self-closing.
3. Tags are nested properly, so the element that opened last closes first.
4. Attribute values are in quotes.
5. Special characters inside text are escaped.
6. Names are spelled the same way in the opening and the closing tag, including capital letters, because XML is case sensitive.

If any rule is broken, the document is not XML, and programs will refuse to read it.

## Finding errors

When the structure is broken, the tool tells you where. It checks the nesting of tags, unclosed tags and comments or CDATA sections that are never closed, and it reports the line and column of the problem together with what it expected.

The most common errors are easy to recognise.

- A closing tag that does not match the opening tag, which is often a typo or a wrong capital letter.
- A tag that was opened and never closed, usually found at the end of the document.
- A tag that closes too early because two elements overlap.
- An ampersand that was not escaped, for example in a company name or a link.
- A comment that was started and never finished.

Fix the first error and check again. One mistake often causes a chain of messages, and fixing the first one removes the rest.

## Escaping special characters

Some characters have a meaning in XML and cannot appear as plain text inside content. The five to remember are the ampersand, the two angle brackets and the two kinds of quotation mark.

They are written as entities: the ampersand as &amp;, the less-than sign as &lt;, the greater-than sign as &gt;, the double quote as &quot; and the apostrophe as &apos;. If a company is called Smith and Sons and you write an ampersand in the name, the document breaks until you replace it with the entity.

## What a formatter cannot check

A formatter checks that XML is well-formed. It does not check that the content makes sense.

- It does not validate against a DTD or an XSD schema, which are the documents that define which elements and attributes are allowed and in which order.
- It cannot tell you that a date is wrong, that a number is out of range or that a required element is missing.

A document can be well-formed and still be rejected by the system that receives it, because it does not follow that system's schema. For that, you need a validator that knows the schema. Use the formatter first to make sure the structure is sound, and then run schema validation where the schema lives.

## Comparing two versions

When a configuration file or feed changes, the quickest way to see what is different is to format both versions the same way and compare them. <tool_text_diff_checker>Text Diff Checker</tool_text_diff_checker> shows added and removed lines. Formatting first matters, because a minified file is one line, and a comparison of two long lines tells you almost nothing.

## Common mistakes to avoid

- Forgetting to escape an ampersand in text or in a link.
- Mixing capital and small letters in opening and closing tags.
- Leaving a tag open when copying only part of a document.
- Assuming that a well-formed file is also valid for the receiving system.
- Comparing minified files instead of formatting them first.

## A quick checklist

1. Paste the XML and format it.
2. Read the first error, fix it and check again.
3. Escape special characters in text.
4. Remember that schema validation is a separate step.
5. Format both versions before you compare them.

:::faq Frequently asked questions
Q: How thoroughly is the XML validated?
A: The tool checks tag nesting, unclosed tags and unterminated comments or CDATA. It does not validate against a DTD or XSD schema.

Q: What is the difference between format and minify?
A: Format adds indentation and line breaks so the structure is easy to read. Minify removes the extra whitespace to make the text as short as possible.

Q: Why is my XML rejected even though the formatter accepts it?
A: The formatter checks that the XML is well-formed. The receiving system may also require that it follows a schema.

Q: How do I use an ampersand in XML text?
A: Write it as the entity &amp; so the document stays well-formed.

Q: Does formatting change my data?
A: No. Only the whitespace between elements changes.
